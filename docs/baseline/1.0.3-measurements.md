# BastionDesk 1.0.3 — pomiary i ocena zamknięcia baseline'u

## Punkt pomiarowy

Pomiary wykonano 4 września 2026 na branchu `chore/phase-0-baseline`, po
commicie odświeżającym zależności `5da4a7f`. Jest to wersja aplikacji `1.0.3`
wraz z poprawkami fazy 0, a nie niezmieniony historyczny tag `v1.0.3`.

Środowisko pomiarowe:

- MacBook Pro z Apple M4 Pro, 12 rdzeniami i 24 GB RAM;
- OrbStack z Docker Engine `29.4.0`, 12 CPU i 11,73 GiB RAM dla maszyny
  `linux/arm64`;
- 11 usług Compose i zachowane lokalne wolumeny;
- obrazy przebudowane przez `docker compose build --pull`.

Powtarzalny pomiar uruchamia:

```bash
bun run test:baseline:measure
```

Skrypt zatrzymuje kontenery bez usuwania wolumenów, mierzy ponowny start do
stanu healthy, wykonuje po 30 sekwencyjnych żądań do lekkich endpointów,
następnie pobiera pojedynczą próbkę `docker stats` i logiczne rozmiary obrazów.

Są to pomiary lokalne bez współbieżnego obciążenia. Opóźnienia lekkich
endpointów nie są SLO dla pełnego workflow użytkownika ani pomiarem
przepustowości.

### Zasoby w spoczynku

Próbka po optymalizacji została pobrana bezpośrednio po żądaniach HTTP. Łącznie
kontenery zużywały około `1,1 GiB` RAM. Chwilowe `4,34%` CPU obejmowało pracę
PostgreSQL po starcie i nie jest porównywalne z obciążeniem produkcyjnym.
Największe składniki RAM:

| Usługa | CPU | RAM |
|---|---:|---:|
| LLM | 0,34% | 603,7 MiB |
| backend | 0,23% | 165,0 MiB |
| cztery węzły MinIO łącznie | 0,16% | 294,8 MiB |
| PostgreSQL | 3,60% | 43,1 MiB |
| frontend, NGINX, PgBouncer i backup łącznie | 0,01% | 27,3 MiB |

Jedna próbka CPU jest wyłącznie punktem odniesienia dla kolejnych
checkpointów. Nie opisuje szczytów podczas klasyfikacji modelu, uploadu ani
backupów.

Suma logiczna nie oznacza zajętości dysku. Docker współdzieli identyczne
warstwy, w szczególności między czterema obrazami usług MinIO.

Redukcja wynika z użycia oficjalnego wariantu PyTorch CPU oraz usunięcia
rekurencyjnego `chown`, który duplikował całą warstwę środowiska Python.
Model pozostał w `BF16`. Jego około 1,9 GiB wag znajduje się w trwałym wolumenie
`huggingface-model-cache`, a nie w obrazie. Wymuszona druga rekreacja usługi
osiągnęła health w 11,82 s bez ponownego pobrania wag. Rzeczywista klasyfikacja
przez gRPC z mTLS zwróciła dozwoloną kategorię w 16,43 s dla pierwszego żądania
po starcie.

## Końcowa weryfikacja

Po aktualizacji zależności i przed oceną zamknięcia zaliczono:

- brak zaległych aktualizacji według `bun outdated --latest` i
  `uv lock --upgrade --dry-run`;
- `bun run check`;
- 32/32 testy w `bun run test:baseline`;
- pełny `docker compose build --pull`;
- smoke wszystkich 11 usług, publiczne granice API/auth/CSRF i wewnętrzny
  health backendu;
- cztery poprawne przebiegi backup/restore łącznie, w tym przebieg po
  aktualizacji zależności i przebieg czasowy z kroku 5.

## Decyzja zamknięcia

**Baseline jest zamrożony jako mierzalny punkt techniczny, a kryterium
ukończenia fazy 0 jest spełnione. Decyzja dla rozpoczęcia fazy 1: GO.**

Finalna bramka wykonała kontrakty, fixture API dwóch organizacji i pełny
backup/restore. Każdy z 41 blokujących scenariuszy ma wynik `PASS`; raport nie
zawiera `PARTIAL`, `NOT_COVERED` ani `FAIL`. Dowód obejmuje kontrolowany SMTP,
sesje i role, cykl incydentu, pliki w MinIO, audyt, analitykę, rzeczywisty oraz
niedostępny LLM, a także uwierzytelniony backend nad odtworzoną bazą. Raport
końcowy znajduje się w `artifacts/baseline/p0-1788549594681-54976/`.

## Ograniczenia porównania

- Wyniki zależą od hosta, przydziału zasobów i rozgrzanych wolumenów.
- Start nie obejmuje pobierania ani budowania obrazów.
- Pomiary HTTP są sekwencyjne i nie obejmują zalogowanego workflow.
- Próbka zasobów nie zastępuje profilu pod obciążeniem ani dłuższej obserwacji.
- Pomiar pojedynczej klasyfikacji po starcie nie określa p50/p95 inferencji;
  dokładny benchmark modelu wymaga stałego datasetu i wielu przebiegów.
