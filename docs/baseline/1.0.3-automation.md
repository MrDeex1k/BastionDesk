# BastionDesk 1.0.3 — automatyzacja baseline'u

## Zakres kroku 3

Krok 3 automatyzuje krytyczne kontrakty możliwe do wykonania deterministycznie
bez tworzenia pełnego środowiska fixture oraz dodaje smoke test uruchomionego
stacku. Punktem wejścia jest macierz
[`1.0.3-regression-scenarios.md`](./1.0.3-regression-scenarios.md).

Nie jest to jeszcze dowód backup/restore ani kompletne wykonanie wszystkich 58
scenariuszy z rzeczywistym SMTP, WebAuthn i dwiema organizacjami. Te elementy
pozostają jawnie w krokach 4–5.

## Pakiety i polecenia

| Pakiet | Polecenie | Zakres |
|---|---|---|
| `baseline-contract` | `bun run test:baseline:contract` | schematy administracyjnego `QUERY`, walidacja dokumentów base64 i kontrakt klienta gRPC |
| `baseline-tenant` | `bun run test:baseline:tenant` | rola administratora przy dodawaniu członka, aktywny tenant, nierozróżnialne ID obcego incydentu i tenant scope zapytań admina |
| `baseline-workflow` | `bun run test:baseline:workflow` | odrzucenie błędnych uploadów przed storage i zapis poprawnego PDF pod kluczem serwerowym |
| wszystkie pakiety Bun | `bun run test:baseline` | 30 testów backendu w trzech pakietach |
| integracja publiczna | `bun run test:baseline:integration` | wersja API, brak sesji, CSRF i origin przez NGINX |
| smoke Compose | `bun run test:baseline:smoke` | gotowość 11 usług, brak unhealthy, integracja publiczna i wewnętrzny `/health` backendu |

Smoke test najpierw waliduje konfigurację, następnie czeka do 180 sekund na
gotowość usług. Limit można jawnie zmienić przez
`BASELINE_SMOKE_TIMEOUT_SECONDS`. Test integracyjny przyjmuje opcjonalny
`BASELINE_BASE_URL` i nie zapisuje tokenów ani cookies poza katalogiem
tymczasowym usuwanym po przebiegu.

## Zamknięte luki `G0`

| Scenariusz | Zmiana | Dowód automatyczny |
|---|---|---|
| `ORG-02-06` | `add-member-by-email` autoryzuje administratora przed wyszukaniem użytkownika i zawsze używa aktywnej organizacji | próba pracownika i jawny obcy `organizationId` są odrzucane bez utworzenia członkostwa |
| `INC-02-04` | tenant scope jest częścią zapytania o incydent | obcy i nieistniejący zasób zwracają ten sam `404 INCIDENT_NOT_FOUND` |
| `INC-03-03` | JSON/base64 ma ścisłą składnię, limit 50 MiB, allowlistę MIME, zgodność rozszerzenia, bezpieczną nazwę i kontrolę sygnatury | błędne dane nie wywołują storage; poprawny PDF dostaje klucz generowany przez serwer |

Test klienta LLM wykazał też błędne rozwiązywanie ścieżki `proto` poza obrazem
backendu. Ścieżka wskazuje teraz repozytoryjny katalog `/proto`, a kontrakt
sprawdza trzy dozwolone kategorie oraz mapowanie timeoutów i niedostępności.

## Pierwszy przebieg

Pierwszy przebieg wykonano 4 września 2026 na branchu
`chore/phase-0-baseline`, na worktree opartym o commit `35868f4`:

- `bun run test:baseline`: 30 zaliczonych, 0 błędów;
- `bun run check`: lint, typecheck i format dla backendu i frontendu zaliczone;
- produkcyjny build backendu, frontendu, NGINX i LLM przez Compose: zaliczony;
- `bun run test:baseline:smoke`: 11 usług gotowych, integracja publiczna i
  health backendu zaliczone.

Pierwszy smoke ujawnił dwa problemy uruchomieniowe, które zostały poprawione i
potwierdzone kolejnym przebiegiem:

1. MinIO zgłaszał health przed utworzeniem bucketa, przez co backup wpadał w
   restart loop. Health `storage-1` wymaga teraz dostępności właściwego bucketa
   z poprawnym CA.
2. Dokładna ścieżka `/api` trafiała do frontendu i zwracała przekierowanie na
   wewnętrzny port `8080`. NGINX kieruje ją teraz bezpośrednio do backendu.

## Granica kroku 3

Krok 3 jest ukończony, gdy pakiety Bun, kontrole statyczne, build i smoke
Compose przechodzą, a luki `G0` mają test regresyjny. Krok 4 nie powtarza tej
pracy: przygotowuje fixture obu tenantów, wymusza backup, odtwarza dump do
czystej bazy i porównuje dane oraz izolację po restore.
