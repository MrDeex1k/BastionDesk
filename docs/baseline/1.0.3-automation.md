# BastionDesk 1.0.3 — automatyzacja baseline'u

## Zakres kroku 3

Krok 3 automatyzuje krytyczne kontrakty możliwe do wykonania deterministycznie
bez tworzenia pełnego środowiska fixture oraz dodaje smoke test uruchomionego
stacku. Punktem wejścia jest macierz
[`1.0.3-regression-scenarios.md`](./1.0.3-regression-scenarios.md).

Ten dokument nie jest dowodem backup/restore ani kompletnym wykonaniem
wszystkich 58 scenariuszy z rzeczywistym SMTP i WebAuthn. Osobny dowód restore
z fixture dwóch organizacji znajduje się w
[`1.0.3-restore.md`](./1.0.3-restore.md).

gotowość usług. Limit można jawnie zmienić przez
`BASELINE_SMOKE_TIMEOUT_SECONDS`. Test integracyjny przyjmuje opcjonalny
`BASELINE_BASE_URL` i nie zapisuje tokenów ani cookies poza katalogiem
tymczasowym usuwanym po przebiegu.

## Fixture auth i organizacji

Pierwsza część rozszerzonego wykonania fazy 0 dodaje izolowany overlay
`docker-compose.phase0.yml`. Uruchamia on SMTP Mailpit wyłącznie w wewnętrznej
sieci stacku, udostępnia API na losowym porcie interfejsu loopback, przełącza
backend na kontrolowany SMTP i wyłącza zewnętrzne zapytanie Have I Been Pwned
tylko na czas tego przebiegu. Konfiguracja produkcyjna nadal domyślnie wykonuje
kontrolę kompromitacji hasła.

Skrypt tworzy przez publiczne API `ORG_A`, `ORG_B`, administratorów obu
organizacji, po dwóch analityków i pracowników w `ORG_A`, analityka i pracownika
w `ORG_B`, zweryfikowanego `USER_NO_ORG` oraz niezweryfikowanego
`USER_UNVERIFIED`. Następnie odczytuje rzeczywiste wiadomości weryfikacyjne,
używa zawartych w nich linków, loguje konta i potwierdza sesje, aktywne
organizacje oraz odrzucenie konta niezweryfikowanego. Hasła, cookies i tokeny
istnieją tylko w pamięci procesu.

Druga część rozszerzonego wykonania przechodzi przez te same publiczne ścieżki
API co frontend. Obejmuje dodanie, zmianę roli i usunięcie członka, odrzucenie
operacji pracownika i jawnie obcej organizacji, utworzenie zgłoszeń w obu
tenantach, widoki pracownika i analityka, przypisanie, konflikt równoległego
przypisania, notatkę, raport PDF, sprawozdanie DOCX, binarne pobranie plików dla
trzech ról, administracyjne `QUERY`, statystyki, metryki, audit trail i
rzeczywistą klasyfikację LLM. Po przebiegu skrypt usuwa obiekty fixture z MinIO
i dane z PostgreSQL, zatrzymuje Mailpit, a backend automatycznie wraca do
podstawowej konfiguracji SMTP także po nieudanym teście.

Pierwszy przebieg ujawnił rozjazd schematu po aktualizacji Better Auth do 1.7:
runtime wymaga klucza tożsamości konta `(issuer, accountId)`, podczas gdy baza
nadal używała `(providerId, accountId)`. Aplikacja zachowuje kompatybilną
strategię `issuer`, świeży schemat zawiera wymagane pole, a migracja
`database/migrations/001-better-auth-1.7-account-identity.sql` bezpiecznie
aktualizuje pustą tabelę. Jeśli istnieją stare konta, migracja celowo zatrzymuje
się przed zmianą i wymaga przejrzenia backfillu issuerów zgodnie z pochodzeniem
dostawcy — nie zgaduje namespace'ów OAuth.

## Pierwszy przebieg

Pierwszy przebieg wykonano 4 września 2026 na branchu
`chore/phase-0-baseline`, na worktree opartym o commit `35868f4`:

- `bun run test:baseline`: 30 zaliczonych, 0 błędów;
- `bun run check`: lint, typecheck i format dla backendu i frontendu zaliczone;
- produkcyjny build backendu, frontendu, NGINX i LLM przez Compose: zaliczony;
- `bun run test:baseline:smoke`: 11 usług gotowych, integracja publiczna i
  health backendu zaliczone.

Pierwszy smoke ujawnił dwa problemy uruchomieniowe, które zostały poprawione i
potwierdzone kolejnym przebiegiem:

1. MinIO zgłaszał health przed utworzeniem bucketa, przez co backup wpadał w
   restart loop. Health `storage-1` wymaga teraz dostępności właściwego bucketa
   z poprawnym CA.
2. Dokładna ścieżka `/api` trafiała do frontendu i zwracała przekierowanie na
   wewnętrzny port `8080`. NGINX kieruje ją teraz bezpośrednio do backendu.

Pierwszy pełny przebieg API ujawnił i zamknął dwie dalsze regresje:

1. Po aktualizacji Better Auth `ctx.json(body, { status })` nie ustawiał już
   statusu HTTP w helperze `add-member-by-email`. Błędy są teraz zgłaszane jako
   `APIError`, więc frontend otrzymuje rzeczywiste `403`, `404` lub `409`.
2. Express 5 udostępnia `req.query` przez getter. Middleware walidacji mutował
   obiekt tymczasowy, przez co wartości domyślne paginacji znikały i endpoint
   `/api/incidents/my` przekazywał `NaN` do PostgreSQL. Zwalidowane query jest
   teraz utrwalane na request, a zachowanie ma test regresyjny.

Po poprawkach pełny przebieg zaliczył macierz 10 tożsamości, izolację dwóch
organizacji, cały przepływ zgłoszenia, storage, audyt, analitykę oraz trzy
wyniki klasyfikacji z rzeczywistego serwisu LLM.

## Raport i bramka P0

Manifest [`scripts/phase0-p0-manifest.ts`](../../scripts/phase0-p0-manifest.ts)
mapuje każde blokujące ID na pakiet dowodowy i określa aktualny poziom pokrycia:
`full`, `partial` albo `missing`. Runner porównuje manifest bezpośrednio z
macierzą Markdown; liczba inna niż 41, duplikat, brakujące albo nadmiarowe ID
przerywają wykonanie.

Każdy przebieg `bun run test:baseline:p0` uruchamia pakiety `baseline`,
`fixture` i `restore`, a następnie zapisuje pod
`artifacts/baseline/p0-{RUN_ID}/` raporty `report.json`, `report.md` oraz logi
pakietów. Artefakty zawierają SHA Git, wersję Bun, skróty schematu i proto,
obrazy Compose oraz wynik każdego ID. Katalog jest ignorowany przez Git.

Statusy raportu mają znaczenie blokujące:

- `PASS` — pełny zadeklarowany dowód i wszystkie wymagane pakiety zaliczone;
- `PARTIAL` — istnieje automatyczny dowód, ale nie obejmuje całego kontraktu;
- `NOT_COVERED` — brak automatycznego dowodu;
- `FAIL` — wymagany pakiet dowodowy nie przeszedł.

Pierwszy raport z 4 września 2026 wykonał wszystkie trzy pakiety bez błędów,
ale poprawnie zakończył bramkę jako `NO-GO`: `11 PASS`, `24 PARTIAL`,
`6 NOT_COVERED`, `0 FAIL` na 41 scenariuszy. Niepełne `P0` pozostają błędem
polecenia, dlatego runner zwraca kod wyjścia `1`, dopóki wszystkie pozycje nie
osiągną `PASS`.

Kolejny przebieg domknął sześć pozycji bez pokrycia oraz pełną asercję
`autoSignInAfterVerification`. Fixture wykonuje teraz negatywne logowanie,
wylogowanie z unieważnieniem sesji, reset hasła przez Mailpit, atomowy konflikt
sluga organizacji, kontrolowany unassign oraz idempotencję resolve. Wynik bramki
to `18 PASS`, `23 PARTIAL`, `0 NOT_COVERED`, `0 FAIL`: nie ma już scenariuszy
bez automatycznego dowodu, ale faza pozostaje `NO-GO` do domknięcia częściowych
kontraktów.

Finalny przebieg z 4 września 2026 domknął wszystkie 23 częściowe kontrakty.
Fixture obejmuje pełną macierz organizacji i ról, odczyty i mutacje incydentów,
walidację oraz nagłówki wszystkich typów plików, paginację i analitykę,
zachowanie przy niedostępnym LLM oraz API uruchomione nad odtworzoną bazą.
Bramka zakończyła się wynikiem `GO`: `41 PASS`, `0 PARTIAL`,
`0 NOT_COVERED`, `0 FAIL`. Raport przebiegu zapisano w
`artifacts/baseline/p0-1788549594681-54976/`.
