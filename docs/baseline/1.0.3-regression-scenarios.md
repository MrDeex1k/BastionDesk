# BastionDesk 1.0.3 — scenariusze regresji baseline'u

## Cel i status

Ten dokument definiuje stały zestaw scenariuszy dla obecnego backendu `1.0.3`
oraz każdej kolejnej implementacji przejmującej jego zachowanie. Punktem
wejścia jest inwentaryzacja z commita `eeab51f`. Przy każdym wykonaniu należy
zapisać rzeczywisty SHA testowanej wersji. Znane rozbieżności między stanem
`1.0.3` a wymaganym wynikiem bezpieczeństwa są oznaczone jako `G0`; pierwsze
wykonanie ma je wykazać, a faza 0 nie może się zakończyć przed ich usunięciem
albo jawną zmianą kontraktu.

Scenariusze nie są w tym dokumencie oznaczone jako zaliczone. Krok 2 ustala
dane, akcje i asercje. Automatyzacja i pierwsze wyniki powstaną w krokach 3–5.

## Zasady niezmienności zestawu

- Identyfikator scenariusza pozostaje stały między checkpointami.
- Zmiana oczekiwanego zachowania wymaga aktualizacji dokumentu i uzasadnienia
  w ADR albo opisie zmiany kontraktu.
- Nowy backend może zmienić implementację i wewnętrzne tabele, ale nie może
  oznaczyć scenariusza jako zaliczony bez równoważnego efektu widocznego dla
  klienta oraz równoważnej izolacji organizacji.
- Każdy test rozpoczyna się ze znanego stanu fixture albo sam tworzy i usuwa
  swoje dane. Kolejność wykonania nie może wpływać na wynik, poza jawnie
  sekwencyjnymi scenariuszami jednego przepływu.
- Sekrety, tokeny, cookies i treść prywatnych plików nie trafiają do logów ani
  artefaktów testowych.

## Stałe środowisko i dane

### Warunki początkowe

Scenariusze integracyjne używają świeżego schematu z `database/init-sql`,
prywatnego bucketa testowego MinIO, kontrolowanej skrzynki SMTP i kontrolowanej
odpowiedzi klasyfikatora gRPC. Publicznym adresem pozostaje NGINX, np.
`http://localhost:4567`. Testy kontraktowe mogą zastąpić adaptery bazodanowe,
SMTP, storage i gRPC, o ile osobny scenariusz integracyjny potwierdza każde
rzeczywiste połączenie.

Każdy przebieg otrzymuje `RUN_ID`. Slugi, emaile i klucze obiektów zawierają
ten identyfikator, aby równoległe wykonania nie współdzieliły stanu.

## Wspólne asercje bezpieczeństwa

Te asercje obowiązują w każdym pasującym scenariuszu, nawet jeśli tabela
wymienia tylko asercję charakterystyczną dla danego przypadku:

1. Brak sesji dla chronionego endpointu daje HTTP `401` i kod `UNAUTHORIZED`.
2. Brak aktywnej organizacji, członkostwa lub roli daje HTTP `403` z właściwym
   kodem `NO_ORGANIZATION`, `NOT_A_MEMBER` albo `FORBIDDEN`.
3. Modyfikujące żądanie aplikacyjne bez poprawnego originu, cookie CSRF i
   nagłówka `X-CSRF-Token` daje HTTP `403`; baza i storage pozostają bez zmian.
4. Próba odczytu zasobu innego tenant'a nie ujawnia jego opisu, nazw plików ani
   członków. Docelowo zachowuje się jak brak zasobu; znany middleware analityka
   zwraca obecnie rozróżnialne `403 ORGANIZATION_ACCESS_DENIED` (`G0`).
5. Lista, paginacja, filtry i agregaty tenant A nie zawierają ID ani markera
   danych tenant B.
6. Odrzucona operacja nie zmienia rekordu, statusu, przypisania, audytu ani
   obiektów storage.
7. Odpowiedź błędu aplikacyjnego zachowuje strukturę
   `{ success: false, error: { code, message } }`.

| `baseline-tenant` | `ORG-02-*`, `INC-01-04..06`, `INC-02-*`, `INC-03-05` i `INC-04-*` | zero odczytów i mutacji cross-tenant |
| `baseline-workflow` | `AUTH-01..03`, `ORG-01`, `INC-01..03`, `LLM-01-01..03` | pełny przepływ od konta do sprawozdania na rzeczywistych adapterach testowych |
| `baseline-browser` | `AUTH-02-04` i główna ścieżka UI pracownik–analityk–admin | zgodność zachowania przeglądarki i WebAuthn |
| `baseline-restore` | `OPS-01-*` | świeża baza działa po odtworzeniu i zachowuje tenant scope |

Pakiet `baseline-tenant` jest blokujący dla każdego checkpointu migracji
Express → NestJS oraz Better Auth → osobny serwis Elysia. Nie wolno kompensować
braku testu tenant scope ręcznym sprawdzeniem pojedynczej odpowiedzi.

## Format dowodu wykonania

Każdy przebieg zapisuje co najmniej:

- nazwę pakietu, SHA, datę UTC i identyfikator `RUN_ID`;
- wersje Bun, obrazów Compose i schematu/proto;
- liczbę scenariuszy zaliczonych, pominiętych i niezaliczonych;
- dla błędu: ID scenariusza, bezpieczny komunikat, HTTP/gRPC status i miejsce
  artefaktu diagnostycznego;
- dla testów storage: oczekiwaną i otrzymaną sumę SHA-256;
- dla izolacji: identyfikatory tenantów i potwierdzenie braku markera obcego
  tenant'a, bez zapisywania danych prywatnych;
- dla restore: klucz dumpu, liczności przed i po oraz wynik smoke testu.

Zaliczenie pakietu wymaga zera niezaliczonych scenariuszy. Pominięcie `P0` jest
traktowane jak niezaliczenie. Dopuszczalne pominięcia `P1` muszą mieć zapisany
powód i termin usunięcia.

## Granica kroku 2

Krok 2 jest ukończony, gdy ta macierz jest wersjonowana i wszystkie scenariusze
mają jednoznaczne dane, akcję, oczekiwany wynik, priorytet i poziom wykonania.
Krok 3 implementuje pakiety `baseline-contract`, `baseline-tenant` i
`baseline-workflow`; krok 4 wykonuje i zapisuje `baseline-restore`.
